# Aydo in Chinese: multi-language support

Date: 2026-10-31. Status: built (English and Chinese, following the app language).

## Intent

The user runs Aydo themselves and wants it in Chinese when their Paseo app is set to Chinese: every
control, label, hint, dialog and message that Aydo shows should be in Chinese, and the setup interview that
opens when a new assistant is made should be in Chinese too. When the app is set back to English, Aydo is in
English again. Nothing for the user to set inside Aydo: it follows the app.

Why: it is a personal tool, used every day; reading English UI text for a Chinese-speaking user is friction
they should not have to put up with. (The user's words: "方方面面", "界面上所有的控制都应该有中文", "只要系统切换成中文就应该是中文".)

## Goals

1. All user-visible text of the plugin's client UI exists in English and Chinese (`zh-CN`) and follows the
   host app's language, live (no reload).
2. The default setup interview prompt has a Chinese version (and a Chinese files-mode version), chosen by the
   app language when the interview starts. So the default exists in two languages (four texts: English and
   Chinese, each in the MCP and the files-mode form). A prompt the user has set in the settings is theirs: it is
   used as written, in whatever language, and never translated or replaced when the app language changes. Only
   a user who has not changed it gets the default in the language of the app. Resetting to the default goes back
   to the default of the current language. (Decided by the user: "用户自己设置的提示词我们不用翻译……
   只有那个默认的提示词是翻译的，用户只要改了提示词那就用他的".)
3. Text that Aydo builds on the server or in shared code and that ends up displayed in the UI (proposal-card
   descriptions, "after setup" notes, schedule descriptions, journal summaries, day names, approval summaries,
   tool-name labels, file-type labels) is shown in the app language too.
4. `paseo-plugin.json` requires `paseo >=0.13.0` (the first release with the plugin translation API).
5. English stays exactly as it is today.

## Non-goals

- Translating prompts the user never reads: the identity, team, tools, memory, playbook and skill prompts, and
  the plugin's messages into a chat (`[Aydo ...]` notices) stay English. If one of them is displayed in the
  UI (for example a preview of a prompt), the displayed copy is in scope, not the prompt itself. (Decided by
  the user: "只是访谈那一段就可以，别的那些提示词都是隐含的，只要不显示在界面上就行，如果显示在界面上的话我们另说".)
- Translating what bots say, daily logs, raw errors from the daemon or provider, the user's own drafts, bot
  names, instructions, the setup prompt they edited in the settings, and any other content the user wrote.
- Languages other than English and Chinese. The structure must make a third language a matter of adding a file,
  but none is delivered.
- A language switch inside Aydo. The app's setting is the only one.
- Support for hosts older than 0.13 (decided by the user: raise the requirement). No fallback, no feature test
  for the missing API.
- Moving the client off the deprecated `@getpaseo/plugin/client/react-native` entry (decided: not needed now).

## Anti-goals

- A Chinese file with a key English does not have, or with placeholders that differ, **throws when the plugin's
  client loads** (SDK validation in `defineTranslations`). That would take the whole UI down. It must be caught
  by a test, never at run time on the user's machine.
- English text that is still hard-coded in a component and so never translated, found only by the user.
- English output changing by a character (the existing tests and the files-mode prompts depend on it).
- Any network access (the no-network test must stay green; resources are bundled JSON, which the SDK docs say
  Paseo bundles locally).

## Constraints from the SDK (Paseo 0.14.0, verified in the package and the official reference)

- Resources are JSON next to the client code: `en` is required, other locales use canonical tags (`zh-CN`);
  nested objects with string leaves; other locales may leave keys out (fall back to English). Keys may not
  contain `.`. Plurals use `_one`/`_other` etc. with a `count`; interpolation is `{{name}}`.
- UI text: `useTranslation(messages)` gives `{ t, locale }`; outside React (callbacks) `client.i18n.t(messages, key)`.
- Labels the host draws (screen, sidebar, settings and Command Center titles, slash-command descriptions and
  argument hints, button titles) take `messages.message(key)` instead of a string. The registrations in
  `index.client.tsx` need that. Do not store the result of `t` as a persistent label.
- The language is the app's explicit language, else the device's ("System"); changing it updates mounted UI
  without reloading the plugin.
- There is no translation API on the server. The reference says: return language-neutral data from RPCs and
  translate in the client.
- The SDK types are already `^0.14.0` (build 63). The runtime translation API is in 0.13.0 and later
  (0.12.0 does not have it).

## Facts about the code that shape the work

- 78 client files (about 14,800 lines). A rough count: 440 text-bearing props (`title`, `label`, `hint`, `info`,
  `placeholder`, `description`, `actionLabel`, `confirmLabel`, `accessibilityLabel`, `text`, `message`), about
  40 toast, dialog and error strings, a few dozen pieces of JSX text. Five to six hundred strings in all. Many
  strings are built from parts (`${n} ${n === 1 ? "assistant" : "assistants"}`), which need plural keys.
- The setup interview prompt is built **on the client**: `setupPromptText(setup, files)` in `shared/setup.ts`
  is called from `client/BotsSurface.tsx` (two places) and becomes the chat's first message. The server is not
  involved, so the language is known where the prompt is chosen. The settings screen also shows
  `DEFAULT_SETUP_PROMPT` as the placeholder of the prompt box. A prompt the user wrote in settings
  (`setup.prompt`) is used as it is, in any language.
- Text produced in `shared/` or `server/` and displayed by the client includes (from the client's imports):
  `describeSchedule`, `describeCron`, `journalSummary`, `dayName`, `BUCKET_LABELS`, `formatLocalDateTime`,
  `approvalSummary`, `humanizeToolName`, `botToolName`, `getFileTypeLabel`, `projectFoldersNote`,
  `afterSetupNotes`, `displayTitle`, and the proposal card text (`describeChange`, `botDetails`,
  `changeWarnings` in `shared/changes.ts`). Some of these are also used by server code and tests with their
  current English output.
- Some stored values are English text made at creation time: the role templates (names, titles), the default
  name "New bot", preset names.

## What is decided

- Locale tags: `en` and `zh-CN`. Chinese is Simplified.
- Settings screen and the rest of the UI say "assistant" where English says assistant; the Chinese UI uses the
  natural Chinese word for it (builder's choice, one word everywhere; propose it and mark it for the user).
- Version: a new build number and zip, as for every change; `AGENTS.md` updated (languages, the 0.13
  requirement, where strings live).

## Left to the builder (marked as my calls where I lean one way)

- File layout of the resources (one JSON per locale, or split per area), and how keys are named.
- How the shared and server text builders get a language: my lean is a translator argument that defaults to the
  English output, so existing callers and tests do not change; the client passes its `t`. The alternative of
  returning structured data and formatting in the client is acceptable where it is simpler.
- How to catch missing translations and hard-coded English: a test that loads both resource files, checks the
  Chinese keys are a subset of the English ones and the placeholders match, and ideally that no component
  contains a literal English UI string outside an allowlist.
- Whether the Chinese file must be complete (my lean: yes, every key, so nothing falls back to English by
  accident) and how to keep it so when strings are added.
- Date and number formatting with the app locale.
- Stored English values: see "Calls made after review" (settled there).
- Order of work and how to split it into reviewable steps.

## How it is checked

- Unit tests as above, and `tsc`, and the existing suite.
- A run on an isolated Paseo 0.14.0 test instance (own home and port 6897, as in the 2026-10-31 timeline
  check; never the main daemon on 6767): install Aydo, set the app language to Chinese and back, open the
  screens and the new-assistant interview, and confirm no English is left and no error is thrown. What cannot be
  checked that way is stated in `AGENTS.md`.

## Calls made after review (mine, not the user's; to be checked by them)

A fresh reader of the design asked eight questions. Three were answered from the code or the packages, five are
settled here as my calls.

Answered from the code and the packages:

- **Displayed text is built when it is drawn, in the client.** `describeChange`, `changeWarnings`,
  `afterSetupNotes`, `journalSummary`, `approvalSummary`, `describeCron`, `humanizeToolName`, `projectFoldersNote`
  and `displayTitle` are called only from `client/`. A proposal card on the timeline stores only
  `{ proposalId }` (`server/file-tools.ts`) and is drawn by the plugin's timeline renderer in
  `index.client.tsx`. So nothing needs re-translating when the language changes: it is drawn again in the new
  language. `botDetails` is used only by server code (the `get_setup` tool text for a bot) and stays English;
  `describeSchedule` is used on both sides and gets the translator argument.
- **The builder must check one thing**: that `useTranslation` works inside the timeline renderers and
  transformers (`addTimelineRenderer`), not only in screens and panels. If it does not, the card text needs the
  `client.i18n.t` form. The SDK reference says modals and popovers get the same context; it does not name timeline renderers.
- **Paseo 0.14 carries the API.** Its plugin package has `translations.d.ts` and `defineTranslations`, and its server bundle contains `zh-CN`
  strings. Paseo 0.11.x does not (it predates 0.13). So a Chinese app language works on 0.14 and not on 0.11.x.
  Not run: the build was inspected, not started.

My calls:

1. **Which locales mean Chinese.** The UI follows the SDK, which has only `zh-CN`, so another Chinese tag
   (`zh-TW`, `zh-HK`) shows English. The interview prompt follows the same rule so the two never disagree:
   Chinese when the app locale is `zh-CN`, `zh`, or `zh-Hans*`; English for every other locale, including
   Japanese or French. A language other than these two shows English everywhere.
2. **The interview language is fixed when the chat starts**, because the first message carries it. Switching the
   app language later does not change a chat already open. The Chinese version of the prompt tells the
   assistant to talk to the user in Chinese and to write the name, title, description and instructions it
   proposes in Chinese. No English prompt text is touched; the identity prompt stays English and the opening
   message is what sets the language. The files-mode version has a Chinese twin too.
3. **Hard-coded English is checked on a best-effort basis; key parity is a required gate.** Required: a test
   that the Chinese keys are a subset of the English ones, the placeholders match, locale tags are canonical and
   no key contains a dot (the failure that would take the UI down at load). Best effort: a scan for literal
   English UI strings with an allowlist, plus a manual pass and the real run.
4. **Stored English values** (role template names and titles, the default name "New bot", preset names): the
   text is chosen in the language of the moment the bot or preset is made and stored as an ordinary value;
   nothing matches stored text against English afterwards, and nothing already stored is ever translated
   later. The pickers that list the templates show them in the current language. A template's instructions
   (`soul`) are a prompt and stay English.
5. **The Chinese word for "assistant" is 助理**, the word the user used. It is used everywhere the English UI
   says assistant; "team" is 团队. The user can change the word; it is one resource value per place, but the
   same word appears in many strings, so say so early.
